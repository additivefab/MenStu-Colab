# 设计包全面评估与下一步开发

日期：2026-11-03。评估对象：`research_collaboration_design_pack_20261103/`（00–06 与 templates），对照的是已合并到 `main`（`27a8600`）的实现。

## 一、结论

1. **设计包的核心要求已基本落地。** 主要包括：
   - 三个权威来源分开：平台管任务和决定，Git 管代码，运行登记表管运行；
   - 代理产出、实验运行、研究评审三层状态分开；
   - 批准绑定不可变的规范哈希；
   - 执行器主动领取任务，配合租约、对账和幂等提交；
   - 代理不持有 GitHub 写权限，由可信发布服务开 PR；
   - 外发闸门在执行器和平台两侧各查一次；
   - 指标只来自机器产生的文件。

   验收矩阵 26 项中，21 项已有自动化测试（外部系统为模拟）。
2. **“还剩什么”分三类：**
   - **(A) 本地就能做的运维与科研有效性缺口：** 没有 CI、没有定时对账、没有评测次数控制、没有备份恢复演练、复现对比不完整、组会纪要和进展不能“引用为任务”；
   - **(B) 必须接入真实环境的验收：** GitHub App、模型订阅、GPU / Slurm / Apptainer、飞书；
   - **(C) 设计包明确建议暂缓的内容。**
3. **本次执行 A 类，作为第 6 批。** B 类已整理成试点验收路线（第五节），需要你提供真实环境后才能做。

## 三、主要缺口（按影响排序）

1. **没有 CI**：PR 无法自动验证，以后的合并只能靠人工跑测试。
2. **没有补偿对账**：外部事件丢失、执行器失联、通知失败之后，系统停在中间状态，只能人工修数据库。
3. **评测次数无上限**：违背设计包“正式评价集不供无限尝试”的科研有效性要求。
4. **没有备份恢复演练**（T26）。
5. **复现对比缺失**（T22 的平台侧）：同一规范重跑后，无法看出结果是否在容差内一致。
6. **没有试点流程指标**：试点期无法判断这条流程本身是否顺畅。
7. **组会纪要和进展不能引用为任务**：“讨论 → 任务”的入口不完整。
8. **本地无法完整演示闭环**：发布 PR 需要真实的 GitHub App，本地看不到“代理改代码 → PR → 运行 → 结果”的完整过程。
