# 备份与恢复（T26）

日期：2026-11-03（第 6 批 G4）。对应验收项 T26“数据库/存储备份恢复——能恢复关联关系与必要产物，不把失效令牌当有效”，以及审计清单“数据库/产物/密钥分开备份，恢复演练”。

结论先行：
- 本地已实现并演练了完整流程：备份 D1 与 R2、恢复到全新库、核验关联、令牌全部失效。演练由 `npm test` 自动执行，并在本地开发库上手工跑了一遍。
- **生产环境从未执行过**。本文的生产命令是按 Cloudflare 工具写的操作步骤，第一次真实演练前必须先确认下面“生产前提”中的问题。

## 一、三类东西分开备份

| 类别 | 内容 | 存放位置 | 备份方式 | 谁能接触 |
|---|---|---|---|---|
| 数据库 | D1（绑定 `DB`）全部表，包括 `d1_migrations` 和自增计数 | 托管 D1 | `wrangler d1 export` 导出，再由 `backup.mjs` 生成带清单的备份目录 | 超级管理员（运维） |
| 产物 | R2（绑定 `FILES`）全部对象：`runs/<runId>/<path>` 运行产物、`agent-attempts/<id>/change.json` 代理变更、`progress/<学生>/<进展>/<uuid>.<扩展名>` 进展附件，以及未被引用的对象 | 托管 R2 | rclone 同步到本地目录，再由 `backup.mjs` 计算 sha256 写入清单 | 同上 |
| 密钥 | Worker 加密变量、执行器令牌、代理订阅凭据 | 托管平台的加密变量；实验室主机 | **不进数据库备份**；单独保存在密码管理器或离线介质，按第五节轮换 | 只限超级管理员 |

数据库备份里只有令牌的**哈希**，没有任何明文密钥。备份脚本根本不读取 Worker 环境变量。

## 二、备份目录与清单

`backup.mjs` 每次生成一个 `backup-<UTC 时间>` 目录。`manifest.json` 最后写入：没有它的目录就是没写完的备份。

```
backup-20261103T102010Z/
  manifest.json            格式、schema 版本、各表行数与文件哈希、R2 对象清单（key、大小、sha256、Content-Type）
  d1/schema.json           sqlite_master 中的建表、索引、触发器语句；按外键排好的导入顺序；自增计数
  d1/tables/<表>.jsonl     第一行是列名，之后每行一条记录（保留 INTEGER / REAL / TEXT / BLOB 存储类型）
  r2/blobs/<sha256>        对象内容，按哈希存放（对象 key 不会变成文件路径）
```

清单中还会记录：
- 备份时数据库引用的对象有多少、有几个对象没被引用；
- **源库预检**：备份时源库本身就缺失或哈希不符的对象。这样恢复核验失败时，能分清是原来就坏了，还是恢复过程弄坏的。

如果某个文本单元格看起来像真实凭据（`ghs_` / `ghp_` / `github_pat_` 令牌、私钥块、`sk-` 开头的 API key、Slack 令牌），备份会被拒绝，并只报告表名、列名和行号。确认是误报后，可以加 `--allow-secret-findings` 重跑；这次放行会记录在清单里。

### 敏感字段的处理

| 字段 | 备份 | 恢复后 |
|---|---|---|
| `app_sessions.token_hash` | 导出（会话 cookie 的 SHA-256） | **整表清空**，所有人需重新登录 |
| `lab_runners.token_sha256` | 导出 | 全部执行器和代理工作进程**停用**，哈希换成随机值（任何令牌都算不出这个值）；用 `reissue-runner-token.mjs` 重新签发，执行器 ID 不变 |
| `local_credentials.activation_hash` | 导出 | 清空。待激活账号需要管理员重新签发链接 |
| `local_credentials.password_hash` | **有意保留并导出**（scrypt 加盐） | 保留，学生恢复后仍可用原密码登录。代价是备份泄露时会暴露密码哈希，所以备份必须加密存放、限制访问 |
| `local_auth_attempts` | 导出 | 清空（登录限流窗口） |
| `research_outputs.submission_password_ciphertext` | 只导出 AES-GCM 密文 | 保留。需要 Worker 密钥 `RESEARCH_OUTPUT_CREDENTIALS_KEY` 才能解密，这个密钥单独备份 |
| GitHub 安装令牌 | 不存在：每次请求现取，有效期 1 小时，从不写入 D1 或 R2（`lib/github/tokens.ts`） | 无需清除。恢复脚本会检查所有表中是否出现了可能存放令牌的新列 |

**关于保留密码哈希**：保留，是为了恢复后 26 名学生不必全部重置密码。替代做法是恢复后清空 `password_hash`，由超级管理员逐个签发一次性设置链接。如果备份介质曾经脱离控制，应该采用替代做法。

## 三、命令

建议在 `package.json` 增加以下脚本（本批未修改该文件）：

```json
"ops:backup": "node scripts/ops/backup.mjs",
"ops:restore": "node scripts/ops/restore.mjs",
"ops:reissue-runner-token": "node scripts/ops/reissue-runner-token.mjs"
```

### 本地（开发库 `.wrangler/state`）

```bash
node scripts/ops/backup.mjs                       # 输出到 .wrangler/backups/（已 gitignore）
node scripts/ops/restore.mjs --backup .wrangler/backups/backup-<时间> --target-state .wrangler/restore-drill/state
node scripts/ops/reissue-runner-token.mjs --runner <执行器 ID> --state .wrangler/restore-drill/state
```

- `restore.mjs` 只往**空库**里恢复。目标库有表或对象时直接拒绝，除非加 `--force`（会先清空目标）。不加 `--force` 时，开发库 `.wrangler/state` 永远不能作为恢复目标。
- 恢复顺序：先核对备份文件哈希；再建表、导入数据（父表在前，外键检查推迟到批次末尾）、写回自增计数、建索引和触发器；然后上传 R2 对象；**先让凭据失效，最后核验**。所以即使核验失败，恢复出来的库里也不会有可用的旧令牌。
- 核验项（任何一项失败，退出码为 2）：
  - 外键 `PRAGMA foreign_key_check`；
  - 各表行数与清单一致（会话表和登录限流表应为 0）；
  - schema 版本与备份一致；
  - 科研闭环关联：任务↔版本、代理尝试↔任务版本、变更请求↔代理尝试（任务、学生、仓库、基线一致）、运行规范↔任务版本与变更请求、运行↔规范与批准哈希、运行事件序号连续、结果指标来源、评审↔结果、跟进任务指回来源运行、父任务、基线、评论回复；
  - 运行规范和结果清单的 sha256 可以重新算出（批准绑定的内容没有被改动）；
  - 数据库引用的每个 R2 对象都存在，且 sha256 与库中记录一致；R2 对象与清单逐个一致，没有多余对象；
  - 恢复前的会话、执行器令牌、激活码全部失效。
- 报告写到 `<target-state>/restore-report.json`。服务上线前可以用 `--verify-only` 重新核验一次。注意：上线后有人重新登录，行数就会变化，核验不再适用。
- 核验通过后，把目标目录换成 `.wrangler/state` 即可在开发服务器里使用（先备份旧目录）。

## 四、生产流程

### 生产前提（第一次演练前必须确认）

1. 生产是托管 Sites 项目（`.openai/hosting.json`：D1 绑定 `DB`，R2 绑定 `FILES`）。需要先确认：我们能否用 `wrangler` 访问底层 Cloudflare 账号中的 D1 与 R2；数据库名和桶名是什么；托管平台是否另有导出 / 恢复功能。下面的 `wrangler` 命令以“有账号权限”为前提。
2. 为 R2 创建**只读** API 令牌给 rclone 备份使用；恢复时再临时创建写权限令牌，用完即删。
3. 备份存放在加密介质上（例如用 age 或 gpg 加密后放到校内存储），并与密钥备份分开存放、分开授权。

### 备份（建议每周一次，每次部署迁移前加做一次）

```bash
wrangler d1 export <DB_NAME> --remote --output d1-$(date -u +%Y%m%dT%H%M%SZ).sql
rclone copy r2:<BUCKET_NAME> ./r2-objects --checksum
node scripts/ops/backup.mjs --d1-sql d1-<时间>.sql --r2-dir ./r2-objects --out <加密卷>/backups
```

第三步把导出结果装进临时本地库，生成与本地备份相同格式、带清单和预检的备份。先导出 D1、再同步 R2，这样数据库引用到的对象一定已经存在；R2 中多出来的新对象只会算作“未引用”。

**已知问题（本地实测）**：`wrangler d1 export` 按 sqlite_master 顺序输出。本库的子表数据会出现在父表建表语句之前，例如 `agent_attempt_events` 早于 `agent_attempts`。因此直接 `wrangler d1 execute --file` 回放这个导出文件，会报 `no such table: main.agent_attempts`。`backup.mjs --d1-sql` 自己解析导出文件：先建所有表，再按外键顺序导入，所以不受影响。**不要把原始导出文件直接回放到新库。**

D1 自带 Time Travel（时间点恢复），可以作为“原库回滚”的快速手段（`wrangler d1 time-travel info / restore`）。但它是在原库上就地回滚，**不会让会话和执行器令牌失效**。回滚后必须立刻执行：

```sql
DELETE FROM app_sessions;
UPDATE lab_runners SET status = 'disabled', token_sha256 = 'revoked-by-restore:' || lower(hex(randomblob(24)));
UPDATE local_credentials SET activation_hash = NULL, activation_expires_at = NULL WHERE activation_hash IS NOT NULL OR activation_expires_at IS NOT NULL;
DELETE FROM local_auth_attempts;
```

### 恢复到新库

1. 在本地全新目录恢复并核验，同时导出给生产用的文件：
   ```bash
   node scripts/ops/restore.mjs --backup <备份目录> --target-state ./restore/state \
     --emit-sql ./restore/sql --emit-r2-dir ./restore/r2
   ```
   `d1-restore.sql` 由**已核验、已让凭据失效**的库生成：每行一条语句；先建全部表，再按外键顺序插入，最后建索引和触发器。自增计数单独放在 `d1-sequences.sql`，因为托管 D1 是否允许写 `sqlite_sequence` 尚未验证。
2. 新建数据库并导入：
   ```bash
   wrangler d1 create <新库名>
   wrangler d1 execute <新库名> --remote --file ./restore/sql/d1-restore.sql
   wrangler d1 execute <新库名> --remote --file ./restore/sql/d1-sequences.sql
   ```
3. R2 恢复到新桶：`rclone copy ./restore/r2 r2:<新桶名> --checksum`。可以用 `./restore/r2.index.tsv` 中的 sha256 抽查。应用读取对象时不依赖 R2 的 Content-Type 或自定义元数据，所以 rclone 不能还原这两项不影响使用。
4. 回读核验：`wrangler d1 export <新库名> --remote --output restored.sql` 和 `rclone copy r2:<新桶名> ./restored-r2`，然后执行 `backup.mjs --d1-sql restored.sql --r2-dir ./restored-r2`。把得到的清单与原备份逐表比较：除会话表和登录限流表为 0、`lab_runners` 和 `local_credentials` 两张表的文件哈希不同外，其余表文件的 sha256 应完全相同。
5. 把 Worker 的 D1 和 R2 绑定切换到新库和新桶（托管平台操作），部署后检查 `/api/health/ready`，schema 一项应为 pass。
6. 对每个执行器和代理工作进程执行
   `node scripts/ops/reissue-runner-token.mjs --runner <ID> --emit-sql reissue-<ID>.sql`，再用 `wrangler d1 execute <新库名> --remote --file reissue-<ID>.sql` 导入。令牌文件（权限 0600，不会打印到终端）放到对应主机的 `tokenFile` 或 `TANYAN_LAB_RUNNER_TOKEN`，然后删除本地副本。
7. 恢复时处于租约中的运行和代理尝试，会原样恢复。执行器重新签发令牌后，再由租约过期和对账流程（G2）收尾。

## 五、密钥在哪里、怎么轮换

| 密钥 | 位置 | 轮换方法 | 恢复时 |
|---|---|---|---|
| `GITHUB_APP_PRIVATE_KEY` | Worker 加密变量 | 在 GitHub App 设置中生成新私钥，更新变量并部署，然后删除旧私钥 | 不随数据库恢复；安装令牌会按需重新获取 |
| `GITHUB_WEBHOOK_SECRET` | Worker 加密变量和 GitHub App | 两边同时换新值 | 停机期间丢失的 webhook，可在 GitHub App 的“Recent Deliveries”中重新投递，或等对账处理 |
| `GITHUB_APP_ID` / `GITHUB_APP_SLUG` | Worker 变量（不是秘密） | 不需要轮换 | — |
| 飞书 `FEISHU_APP_SECRET`、`FEISHU_BOT_APP_SECRET`、`FEISHU_*VERIFICATION_TOKEN`、`FEISHU_*ENCRYPT_KEY` | Worker 加密变量；长连接 bridge 的 `run-bridge.zsh` | 在飞书开放平台重置，同时更新站点和 bridge | 不随数据库恢复 |
| `RESEARCH_OUTPUT_CREDENTIALS_KEY`（旧名 `RESEARCH_OUTPUTS_ENCRYPTION_KEY`、`RESEARCH_OUTPUT_PASSWORD_KEY`） | Worker 加密变量 | **不能直接更换**：已保存的投稿密码是用它加密的，换掉后就无法解密。目前没有重新加密工具（待办）。必须单独、离线备份 | 恢复后的数据库只能配合原密钥使用；密钥丢失时，学生需重新填写投稿密码 |
| 执行器 / 代理工作进程令牌 | 实验室主机的 `tokenFile` 或 `TANYAN_LAB_RUNNER_TOKEN`；平台只存哈希 | `reissue-runner-token.mjs`（执行器 ID 不变） | 恢复后全部失效，必须重新签发 |
| 代理订阅凭据（Codex / Claude） | 只在代理工作进程主机的 profiles 目录中 | 在对应主机上重新登录 | 平台不保存，与恢复无关 |
| 用户会话 | 平台只存哈希 | — | 恢复后全部失效 |

## 六、演练频率

- **每周**：生产自动备份（D1 导出、R2 同步、`backup.mjs` 生成清单），保留最近 8 份周备份和 6 份月备份。
- **每次部署数据库迁移前**：额外备份一次。
- **每月**：取最近一份生产备份，在本地全新目录跑一次 `restore.mjs`，核验必须全部 pass，结果记入下面的演练记录。
- **每季度**：完整走一遍第四节“恢复到新库”，恢复到临时的新 D1 库和新 R2 桶，最后删除。
- `npm test` 每次都会运行自动演练 `tests/ops-backup-restore.test.mjs`。

## 七、本地已验证 / 未验证

### 已验证（2026-11-03，本地）

1. **自动演练**（`tests/ops-backup-restore.test.mjs`，Miniflare 运行构建好的 Worker，外网全部阻断）：
   - 数据：通过真实接口造出一条完整闭环：任务 → 代理尝试（`change.json` 在 R2）→ 变更请求 → 批准的运行 → 两个 R2 产物 → 结果 → 采纳的评审 → 评论 → 跟进任务（谱系）；另有一个租约中的运行、一个进展附件、一个未引用对象，以及本地密码和待激活账号；
   - 备份：清单中的行数与源库一致，R2 sha256 正确；签发过的执行器令牌和会话 cookie 明文不出现在备份的任何文件中；疑似凭据的数据会被拒绝；
   - 恢复：在全新实例上全部核验通过，跟进任务的来源运行、父任务和自增计数完全一致；
   - 旧会话 cookie 访问 `/api/runs` 和 `/api/run-artifacts` 返回 401；两个旧执行器令牌访问 `/api/lab/runs` 返回 401（`RUNNER_AUTH_INVALID`）；`/api/health/ready` 的 schema 项为 pass（v27）；
   - 重新登录、重新签发令牌后，结果、指标和产物字节与原来一致，旧令牌仍然无效；
   - `--emit-sql` 的输出逐行回放后，得到的库同样核验通过；
   - 目标库不是空的、或备份文件被篡改时，拒绝恢复；人为删掉一个产物、改动一个运行规范、断开一条谱系，核验能准确报出这几项；
   - `wrangler d1 export` 格式的导入器能处理子表早于父表、带分号或换行的字符串、触发器和统计表。
2. **手工演练**（本地开发库，用 `npm run db:migrate:local`、`dev:admin` 和 `seed-research-loop.mjs` 造数据）：
   - 备份：71 张表、385 行、24 个 R2 对象，24 个对象全部被数据库引用；
   - 恢复到新目录：24 项核验全部 pass，完整闭环链 5 条；
   - 再次往同一目录恢复被拒绝；以开发库为目标也被拒绝；
   - `--emit-sql` 生成的 SQL 用 `wrangler d1 execute --local --file` 导入成功；
   - 用 `wrangler d1 export --local` 导出（与 `--remote` 是同一导出逻辑，只是数据来源不同），再经 `backup.mjs --d1-sql` 生成备份：71 张表的数据文件与直接备份逐个相同，恢复后 24 项全部 pass；
   - `reissue-runner-token.mjs` 两种模式（直接写本地库、生成 SQL）都可用，重新签发后 `--verify-only` 仍然通过。

### 未验证

- 对托管 D1 和 R2 的任何操作：`--remote` 导出与导入、托管 D1 对文件大小 / 语句的限制、是否接受 `PRAGMA defer_foreign_keys` 和 `sqlite_sequence` 写入、rclone 与 R2、托管 Sites 平台的访问权限与绑定切换、Time Travel。
- 真实数据量下的耗时。目前实现会把整张表读进内存，按现有规模（几十名学生）没有问题；数据增长到几十万行以上时，需要改成流式处理。
- 密钥轮换的实际操作（GitHub App 私钥、飞书、投稿密码密钥）。
- 实验室主机上的状态（执行器本地调度记录、代理工作目录）不在备份范围内；这些状态由租约过期和对账流程恢复，没有做过演练。
