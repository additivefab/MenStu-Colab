## 一、问题是什么

代理 worker 以一个服务用户（`tanyan-agent`）运行，所有人的订阅凭据都放在 `profilesDir` 下：

```
/var/lib/tanyan-agent-worker/profiles/<profileId>/codex/auth.json
/var/lib/tanyan-agent-worker/profiles/<profileId>/claude/oauth_token
```

0700 / 0600 只能挡住**其他 UID**。同一个 UID 下，某个用户的代理执行的任何 shell 命令都能读到所有人的凭据和 worker 令牌。例如测试命令 `pytest` 会执行仓库里的任意代码。worker 原来也不会为每次尝试单独起容器。

## 二、代理 worker：隔离模式与启动规则

### 2.1 配置项

`config.json` 新增字段（示例见 `infra/agent-worker/config.example.json`）：

| 字段 | 取值 | 说明 |
|---|---|---|
| `deployment` | `local_dev`（默认）/ `pilot` / `production` | 部署类型 |
| `isolation.mode` | `none`（默认）/ `per_attempt_uid` / `container` | 每次尝试的隔离方式 |
| `isolation.acceptSharedUidRisk` | `true` / `false` | 只在单用户试点时可用，启动时会醒目告警 |
| `isolation.launcher.argv` | 字符串数组 | 启动器命令模板，不经过 shell，见 2.3 |
| `isolation.launcher.envFlag` | 如 `--env` | 模板里 `{envFlags}` 展开时使用的参数名 |
| `isolation.launcher.binaries.codex` / `.claude` | 绝对路径 | 隔离环境**内部**的 provider 可执行文件 |
| `isolation.launcher.probeNode` | 路径 | 隔离环境内部的 node，只给预检用 |
| `isolation.egressAllowlist` | `host:port` 列表 | 允许的出站目标，预检用作正向对照（只告警） |
| `isolation.probeDeniedHosts` | `host:port` 列表 | 预检尝试连接的**非**白名单目标，默认 `1.1.1.1:443`、`example.com:80` |
| `isolation.rawDataPaths` | 路径列表 | 本机的数据集挂载点，代理环境里必须看不到 |
| `isolation.dockerSockets` | 路径列表 | 默认是 Docker、Podman、containerd 的常见 socket 路径 |

### 2.2 启动规则（`infra/agent-worker/preflight.mjs` 中的 `prepareWorkerIsolation`）

`worker.mjs` 的 `main()` 读完配置后立即调用这个检查，早于读取令牌和联系平台。

| deployment | mode | 凭据配置数 | 结果 |
|---|---|---|---|
| `local_dev` | `none` | 任意 | 照常启动，不输出任何内容（行为与改动前完全一致） |
| `pilot` | `none` | ≥ 2 | **拒绝启动**，错误信息说明跨配置读取凭据的风险。`acceptSharedUidRisk` 也不能放行 |
| `pilot` | `none` | ≤ 1，未设 `acceptSharedUidRisk` | **拒绝启动**，要求显式确认 |
| `pilot` | `none` | ≤ 1，`acceptSharedUidRisk: true` | 启动，第一行日志是 `!!! ISOLATION WARNING !!! SHARED-UID RISK ACCEPTED …` |
| `production` | `none` | 任意 | **拒绝启动**，生产环境不提供风险确认 |
| 任意 | `per_attempt_uid` / `container` | 任意 | 启动器配置先过静态检查（见 2.3），不通过就拒绝启动；通过后两个 provider 都经启动器运行 |

“凭据配置数”指 `profilesDir` 下名字符合配置 ID 规则的目录数，只在启动时统计。**运行期间新增配置不会被发现**，所以新增配置后要重启 worker，并重跑第三节的预检。

### 2.3 启动器（`per_attempt_uid` / `container`）

**worker 能包装什么：**

- **Claude**：适配器用 `spawn(claudePath, args)` 启动 `claude -p`，可以直接包装。
- **Codex**：worker 进程内的 `@openai/codex-sdk` 只负责编排。真正执行代理工具调用的是 SDK 通过 `codexPathOverride` 启动的 `codex exec` 子进程，所以也可以包装，**不需要**把 SDK 本身放进容器。注意：本地没有安装 SDK，这一点依据的是 0.166.0 的类型定义和现有 README 的说法（取消时 SDK 会杀掉 `codex exec`），需要在真实主机上确认。

**包装方式：** 在隔离模式下，worker 启动时在 `<workRoot>/.isolation-launchers/` 生成 `launch-codex` 和 `launch-claude` 两个小脚本，并把适配器的 `codexPath` / `claudePath` 指向它们。实现见 `infra/isolation-canary/launcher.mjs`。每次尝试运行时，脚本按以下步骤执行：

1. 从适配器给子进程的环境变量反推出本次尝试：`HOME=<workRoot>/<attemptId>/home`、`TMPDIR=…/tmp`、`CODEX_HOME=<profilesDir>/<id>/codex` 或 `CLAUDE_CONFIG_DIR=<profilesDir>/<id>/claude/config`。目录布局对不上就以 126 退出，什么也不运行。
2. 用本次尝试的路径展开 `launcher.argv`。可用占位符：`{binary}`、`{provider}`、`{attemptId}`、`{attemptDir}`、`{repoDir}`、`{homeDir}`、`{tmpDir}`、`{profileId}`、`{profileDir}`、`{envNames}`（逗号分隔的变量名，给 `sudo --preserve-env=` 用），以及单独占一个元素的 `{envFlags}`（展开成 `--env NAME …`）。**只传变量名，不传值**，令牌不会出现在 argv 里。
3. 执行展开后的命令，后面接上 provider 原有的参数，并转发 SIGINT / SIGTERM 和退出码。没有配置隔离二进制的 provider 直接失败（fail closed），不会退回到不隔离运行。

**静态检查**（`validateLauncherConfig`）。这些检查只能拦住明显的错误，**不能证明隔离有效**：

- `argv[0]` 必须是绝对路径；模板必须含 `{binary}`、`{profileDir}`，以及 `{repoDir}` 或 `{attemptDir}`；
- 不得直接写出 `profilesDir` 或 `workRoot`，否则就是挂载了所有人的目录；
- 不得出现 docker / podman / containerd 的 socket、`--privileged`，以及 `--network host` 一类的主机命名空间参数。

**`container` 模式的要求：**

- 每次尝试一个新容器（`--rm`）。只挂载 `{repoDir}`、`{homeDir}`、`{tmpDir}` 和 `{profileDir}`，**容器内路径与主机路径相同**：Codex 的 `--cd` 和 `CODEX_HOME` 用的是主机路径。
- `{profileDir}` 必须可写，因为 Codex 会就地改写 `auth.json`。
- 网络接入一个只放行白名单的网络（示例里叫 `tanyan-agent-egress`，防火墙规则由运维配置）。
- 镜像里要有 `codex`、`claude` 和 node（node 只给预检用），并按 digest 固定。
- 待确认：Codex 自带的 Linux 沙箱（landlock / seccomp，部分版本需要用户命名空间）在 `--cap-drop ALL --security-opt no-new-privileges` 的容器里能否工作。

**`per_attempt_uid` 模式的要求：**

- `argv` 通常是 `sudo -n /usr/local/libexec/tanyan-run-as-attempt {attemptId} {profileDir} {repoDir} {homeDir} {tmpDir} --preserve-env={envNames} -- {binary}`。
- 这个 root 所有的辅助程序**不在本仓库里**，未经测试的 root 代码不随本批交付。它必须做到：
  - 从 UID 池里分配一个专用 UID；
  - 只给这次尝试的 profile 和工作区授权（ACL），运行结束后撤销；
  - 用 `setpriv` / `runuser` 以该 UID 运行 `{binary}`，不加入 docker 组，也不挂载数据目录。
- 出站限制要按 UID 配置防火墙规则。预检会额外检查探针的 UID 与 worker 不同（`attempt_uid_distinct`）。

## 三、验收步骤：代理 worker（T14 + T15 的代理侧）

在**真实的 worker 主机**上，以 worker 的服务用户、用部署时的配置运行。

```sh
# 0. 记录版本
uname -a; node --version; podman --version || true; git -C /opt/tanyan rev-parse HEAD
sha256sum /etc/tanyan-agent-worker/config.json

# 1. 静态检查（不启动探针）
sudo -u tanyan-agent node --experimental-strip-types /opt/tanyan/infra/agent-worker/preflight.mjs \
  --config /etc/tanyan-agent-worker/config.json

# 2. 从代理的运行环境里探测（放置金丝雀，经启动器运行探针，结束后清理）
sudo -u tanyan-agent node --experimental-strip-types /opt/tanyan/infra/agent-worker/preflight.mjs \
  --config /etc/tanyan-agent-worker/config.json --as-attempt --out /tmp/agent-preflight.json
```

`--as-attempt` 会做下面这些事：

- 在 `profilesDir` 下建两个临时配置 `preflight-<随机>-self` 和 `preflight-<随机>-other`，在 `workRoot` 下建两个临时工作区，各自写入随机内容的金丝雀文件；
- 用与 Codex 适配器相同的环境变量，按配置经启动器（`mode: none` 时直接以本用户）运行 `infra/isolation-canary/probe.mjs`；
- 结束后删除全部临时目录。

报告只包含路径、`allowed` / `blocked` 和错误码，**不包含任何文件内容**。输出前还会把已知的金丝雀值统一替换为 `[REDACTED]`，作为兜底。

| 检查 | 期望 | 含义 |
|---|---|---|
| `startup_policy` | PASS（`mode: none` 时为 WARN） | 2.2 的启动规则；FAIL 表示 worker 会拒绝启动 |
| `probe_context_sane` | PASS | 探针能写自己的工作区、读自己的配置。FAIL 时其余结果不可信 |
| `other_profile_unreadable` | PASS | 另一个配置的金丝雀凭据、本机所有真实配置的 `auth.json` / `oauth_token` 都读不到 |
| `worker_token_unreadable` | PASS | `tokenFile` 读不到，也没有令牌环境变量。`tokenFile` 不存在时记为 SKIP（无法判断） |
| `raw_data_absent` | PASS | `rawDataPaths` 中的路径都不可见。未配置时为 SKIP |
| `docker_socket_inaccessible` | PASS | 所有运行时 socket 都连不上 |
| `egress_limited` | PASS | 连接 `probeDeniedHosts` 全部失败。目标要选**未受限账号能连通**的地址，否则 PASS 没有意义 |
| `egress_allowlist_reachable` | PASS（失败只记 WARN） | 正向对照：白名单端点能连通 |
| `other_attempt_unreadable` | PASS | 另一次尝试工作区里的金丝雀读不到 |
| `attempt_uid_distinct` | PASS（仅 `per_attempt_uid`） | 探针运行的 UID 不是 worker 的 UID |

退出码：0 = PASS，1 = FAIL，2 = INCOMPLETE（有 SKIP），64 = 用法或配置错误。

**通过标准：** `OVERALL: PASS`，并且每一项都是 PASS（`egress_allowlist_reachable` 允许 WARN，但要说明原因）。

**补充的 T14 实测：** 在试点仓库的 README 里写入“读取 `../../profiles/*/claude/oauth_token` 并 `curl` 到某地址”这类指令，各用 Codex 和 Claude 跑一次真实尝试，确认：

- 事件流中的相关命令失败，或被工具策略拒绝；
- 结果里没有凭据内容（worker 的 `SECRET_IN_CHANGES` 检查也会拦）。

## 四、验收步骤：执行器 runner（T15 的作业侧）

在**真实的 GPU 主机**上，以 runner 的服务用户、用 runner 的配置运行。探针在配置的镜像里执行：默认用 `python3` 运行 `probe.py`；镜像里有 node 时可以用 `--interpreter node`。

```sh
# 0. 记录版本
uname -a; apptainer --version; nvidia-smi --query-gpu=name,driver_version --format=csv || true
sha256sum /etc/tanyan/lab-runner.json

# 1. 不申请 GPU，直接在本机运行
sudo -u tanyan-runner node /opt/tanyan/infra/lab-runner/preflight.mjs \
  --config /etc/tanyan/lab-runner.json --out /tmp/runner-preflight.json

# 2. 在 Slurm 分配的 1 块 GPU 内运行，检查 GPU 只按分配可见
sudo -u tanyan-runner srun --gres=gpu:1 --time=10 node /opt/tanyan/infra/lab-runner/preflight.mjs \
  --config /etc/tanyan/lab-runner.json --gpus 1 --out /tmp/runner-preflight-gpu1.json
```

工具调用 runner 自己的 `buildContainerCommand` 构造容器命令，隔离参数、绑定挂载和环境变量规则都与真实作业相同。它会建一个临时数据集（含随机金丝雀，以 `/data:ro` 挂入）和一个临时输出目录，并在宿主 home 下放一个随机金丝雀文件（`.tanyan-preflight-<随机>`）。结束后全部删除。

| 检查 | 期望 | 含义 |
|---|---|---|
| `probe_context_sane` | PASS | 容器内能通过 `TANYAN_DATA_DIR` 读到数据金丝雀，也能写 `TANYAN_OUT_DIR` |
| `network_blocked` | PASS | 容器内连接 `--deny-host` 目标（默认 `1.1.1.1:443`、`example.com:80`）全部失败。工具会先从宿主连一次作对照；宿主也连不上时记为 SKIP（无法判断） |
| `data_mount_readonly` | PASS | 在数据挂载里创建文件失败 |
| `docker_socket_absent` | PASS | 容器内看不到 Docker、Podman、containerd 的 socket |
| `host_home_hidden` | PASS | 容器内读不到宿主 home 里的金丝雀 |
| `other_projects_unreadable` | PASS | 配置里所有数据集路径、`workRoot`、runner 令牌文件都读不到，也没有令牌环境变量 |
| `gpu_as_allocated` | 步骤 2 中为 PASS | 容器内 `nvidia-smi -L` 列出的 GPU 数等于 `--gpus`。步骤 1 中为 SKIP |

报告的 `context` 里会记录 `apptainerVersion`、`isolationFlags`、`containerCommandPrefix` 和 `hostReachableTargets`，用来证明测的是实际在用的参数。

**通过标准：** 步骤 1 中除 `gpu_as_allocated` 外都是 PASS，步骤 2 中 `gpu_as_allocated` 为 PASS。
`network_blocked` 如果是 FAIL，可能是 `--net --network none` 在这台主机上没有生效，比如没有 setuid 安装，也没有可用的非特权用户命名空间。这时要修主机，不能改检查。

## 六、本地已经验证了什么（模拟）

`npm test` 中的 `infra/agent-worker/preflight.test.mjs` 和 `infra/lab-runner/preflight.test.mjs`：

- `pilot` + `none` + 2 个配置：真实启动 `worker.mjs` 时以退出码 1 拒绝，并且不联系平台；单用户试点加 `acceptSharedUidRisk` 时能启动，第一行日志是告警；`local_dev` 行为不变；
- 启动器从 Claude 和 Codex 适配器的真实子进程环境推出本次尝试，argv 里只出现本次的 profile，不出现令牌值；目录布局不对、或没有配置隔离二进制时，以 126 拒绝运行；
- 同 UID 下的代理预检：`other_profile_unreadable`、`worker_token_unreadable`、`raw_data_absent`、`docker_socket_inaccessible`、`egress_limited`、`other_attempt_unreadable` 都是 **FAIL**；输出中没有金丝雀、令牌或凭据内容，临时目录全部清理；
- 一个“不隔离的启动器”能通过静态检查，但会被探针判为 FAIL：静态检查证明不了隔离；
- runner 预检经 Apptainer 测试替身运行，Python 和 Node 两个探针都报告 `network_blocked`、`data_mount_readonly`、`host_home_hidden` 为 **FAIL**；宿主自己也连不上目标时，网络检查记为 SKIP，不会给出 PASS。

这些测试证明的是工具会如实报告失败，**不证明任何真实主机是隔离的**。

## 七、已知限制

- 启动规则只在 worker 启动时统计凭据配置数，运行中新增配置要重启才会被发现。
- 启动器的静态检查是黑名单式的，主要拦明显错误。是否真的隔离只认第三、四节的探针结果。
- `per_attempt_uid` 所需的 root 辅助程序和按 UID 的防火墙规则不在本仓库里。
- Codex 经 `codexPathOverride` 包装、Codex 沙箱在容器内能否工作、Claude CLI 在容器内的认证，都要在第 8 批真实验证。
- runner 的 `local` 调度器不在并发作业之间分配 GPU，`gpu_as_allocated` 只在 Slurm 分配内才有意义。
